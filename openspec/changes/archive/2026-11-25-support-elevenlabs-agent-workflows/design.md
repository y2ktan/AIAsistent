# Design

## Context

The hosted-agent validator in `server/internal/api/elevenlabs_agent.go` currently admits only an empty workflow, rejects MCP references and non-system external tools, and verifies the private agent version and client override settings before token issuance. Hosted prompt synchronization patches the prompt/name and Knowledge Base synchronization merges only application-managed document IDs; workflow data is currently outside the patch payload.

Application MCP records in `server/internal/api/store.go` persist the endpoint, encrypted Authorization header, enabled flag, discovered tools, allowlist, and timeout. `mcp.Host` validates outbound URLs and enforces the enabled-tool allowlist, but its current tool-call result exposed to the local agent is sanitized text. Admin CRUD and tool selection live in the existing MCP section of `web/src/app/admin/page.tsx`. There is no inbound MCP gateway or configured public application base URL; `WEB_ORIGIN` is the browser origin and must not be used to construct provider callbacks.

## Goals / Non-Goals

**Goals:**
- Admit supported ElevenLabs workflow graphs and server-side provider tools while retaining private-agent, version, and client-override checks.
- Let an administrator independently select disabled, direct, or proxy integration for each application MCP server.
- Keep the app's discovered-tool allowlist authoritative and make sync ownership, failures, and credential handling explicit.
- Preserve dashboard-managed workflow and tool configuration while reconciling only application-managed MCP resources.

**Non-Goals:**
- Building an application workflow editor or mirroring ElevenLabs' workflow graph into local storage.
- Adding browser client-tool callbacks, a local conversational tool loop to hosted mode, or changing `cascaded`/`realtime` tool behavior.
- Supporting every future or undocumented workflow node, subagent configuration, arbitrary MCP protocol methods, or rich MCP result types beyond the existing sanitized text behavior.
- Automatically sharing existing MCP credentials or enabling hosted MCP integration for existing records.

## Decisions

1. **Validate the provider-owned workflow as a bounded graph.** Extend hosted-agent inspection to parse the documented workflow envelope and supported node/edge shapes, including dashboard `override_agent` nodes, expression conditions, and bounded provider metadata (`version` and empty `subgraphs`). Validate node and edge references and collect every external tool and MCP-server reference from the agent, dispatch nodes, and override-agent configuration. Resolve provider resource IDs through the corresponding ElevenLabs API before admission. Continue rejecting unknown node/tool types, nonempty subgraphs, browser-only tools, malformed references, and client-supplied workflow/tool overrides. Keep the existing private-agent, authenticated-agent, and version checks. Continue rejecting unsupported standalone-agent transfers and standalone subagent configuration. Workflow data remains provider-owned: prompt, document, or MCP synchronization must never include a `workflow` patch.

2. **Treat provider-owned and app-owned tools differently.** Tools already configured in ElevenLabs remain provider-owned and are inspected but never rewritten or deleted by the app. Track each app MCP server's selected mode and its application-owned ElevenLabs MCP resource ID/status alongside the local record. Default new and existing records to `disabled`. Application-managed resources are updated or removed only through that mapping; do not infer ownership from a display name.

3. **Make direct registration deliberately strict.** Direct mode registers the existing public HTTPS endpoint with ElevenLabs and sends the configured Authorization header to the provider only after explicit administrator confirmation. Permit it only when the endpoint passes public-HTTPS eligibility checks and the provider-side registration can represent the complete app allowlist; initially require all discovered tools to be allowlisted. If any discovered tool is excluded, require proxy mode rather than relying on approval prompts as an authorization boundary. Verify provider registration and agent attachment before marking the record synchronized.

4. **Use a separately authenticated application proxy when credentials must stay local.** Add a deployment setting such as `HOSTED_MCP_PROXY_BASE_URL`; proxy mode is unavailable until it is configured as a public HTTPS origin. Build the MCP endpoint from this configured origin and the persisted server ID, never from request headers. The gateway supports only initialization, tool listing, and tool calls; lists only discovered, enabled, allowlisted tools and rejects all other methods before forwarding. Authenticate each request with a dedicated per-server bearer token, keep it encrypted at rest for provider reconciliation, compare authentication in constant time, and never return it from admin APIs or logs. Forward tool calls through the existing `mcp.Host` so outbound URL validation, timeouts, upstream Authorization handling, and allowlist checks remain centralized. Adapt the existing sanitized text result into a valid MCP response; do not add a second arbitrary-URL HTTP client.

5. **Use one idempotent reconciliation path and explicit sync states.** Extend hosted resource synchronization to reconcile selected MCP resources after prompt and Knowledge Base synchronization, and invoke the same reconciler after relevant admin changes. Persist modes, provider resource IDs, and `pending`/`synced`/`failed` (including incomplete revocation) state with the MCP record. Preserve a local record in a disabled/revocation-pending state if provider deletion fails so the mapping can be retried; never report it as revoked. Do not hard-delete its ownership record before remote cleanup is confirmed. Hosted token issuance revalidates the agent version and blocks while a workflow-referenced app resource is pending, failed, or not synchronized. An explicit admin retry reconciles without duplicating remote resources.

6. **Keep the admin flow explicit and observable.** Extend the strict MCP admin request/response model and database persistence with the integration mode, provider resource mapping, and safe sync status/error fields. Add per-server mode selection and credential/external-action disclosures to the existing MCP cards. Show sanitized failure or revocation status and a retry action; never return provider or proxy secrets. A saved local choice can remain visible after a failed provider call, but the API/UI must report it as failed and hosted admission must not treat it as ready. Keep Agent Skills as prompt guidance and validate their tool references against the reconciled hosted tool inventory; skill text cannot create a tool or change its authorization.

7. **Protect the inbound gateway independently of browser sessions.** The proxy route uses only its per-server credential, with bounded request bodies, request timeouts, rate limits, strict JSON-RPC shape validation, and no cookie-based or browser-origin authentication. The route resolves the server from the path, reloads current enabled/allowlist policy for every call, and applies the existing outbound SSRF policy to its endpoint. Invalid credentials and disallowed tools are rejected before contacting the upstream MCP server.

8. **Recover ambiguous creation using durable intent, not another POST.** The documented ElevenLabs MCP creation API does not expose an idempotency key or caller-selected resource ID. Before creation, persist a high-entropy creation-intent ID, the intended provider configuration, and a creation-attempt state alongside the local server. Serialize the transition into an attempted creation durably across application instances; an expired lease or process restart must not authorize another POST after an ambiguous attempt. Include the intent ID as a non-secret, namespaced ownership marker in the documented MCP `request_meta` configuration, which may also be sent to the upstream service with tool calls. Do not put credentials, tool arguments, or conversation data in that marker.

   If creation returns a verifiable resource ID, persist the mapping before attachment. If the response is lost, times out, or cannot prove creation did not occur, retain the intent and mark recovery pending/failed. A retry performs bounded provider listing and a resource GET, and recovers only exactly one resource whose marker and intended configuration match the persisted intent. Persist that verified mapping before updating, attaching, or deleting the recovered resource. A missing match, duplicate marker, mismatched configuration, unavailable listing, or unverified marker remains fail-closed with a sanitized diagnostic; never issue another create merely because listing returned no match. Display names are not ownership evidence. Preserve the creation intent until ambiguous creation is resolved and remote cleanup is verified, including when the server is disabled or deleted locally. Administrator-assisted recovery is required when automatic verification cannot establish a unique mapping.

## Risks / Trade-offs

- [Risk] ElevenLabs workflow or MCP response contracts change, or the configured key lacks MCP-server permissions. → Keep a typed allowlist of supported structures, test representative API fixtures, verify create/update/delete responses, and surface provider permission/schema errors without marking synchronization successful.
- [Risk] Direct mode transfers the endpoint credential to ElevenLabs and can expose every tool registered on that endpoint. → Require explicit confirmation, public HTTPS, exact allowlist eligibility, and an auditable per-server mode; recommend proxy for partial allowlists or credentials that must remain local.
- [Risk] The proxy is externally reachable and could be abused if a per-server credential leaks. → Use per-server high-entropy credentials, encrypted persistence, constant-time checks, revocation, per-server rate limits, bounded payloads/timeouts, sanitized logs, and live policy checks before every call.
- [Risk] Provider-side create/update/delete can fail partway through a mode change or removal. → Persist ownership and sync state, reconcile idempotently, retain disabled records until cleanup succeeds, block affected hosted admission, and explicitly warn when provider-side revocation is incomplete.
- [Risk] An MCP create succeeds but its response or local mapping write is lost. → Persist creation intent before POST and recover by an exact provider-stored marker and configuration match. Block uncertain recovery instead of retrying creation; test timeout-after-create, persistence failure, process restart, concurrent reconciliation, and absent/duplicate/mismatched matches.
- [Risk] A local deployment or reverse proxy may not expose the app to ElevenLabs. → Require a configured public HTTPS proxy origin before proxy mode can be saved; direct mode and disabled mode remain separate options.
- [Risk] Provider workflows may contain unknown or client-executed nodes. → Fail closed with a sanitized, actionable admin error rather than accepting an unverified workflow.

## Migration Plan

1. Add an additive persistence migration for hosted integration mode, provider resource ID, proxy credential, sync status/error, and durable creation-intent ID/configuration/attempt state. Default every existing MCP record to `disabled` with no creation intent; do not provision or share any existing credential during migration. Keep any credentials in the intended configuration encrypted at rest and omit the intent configuration from admin API responses.
2. Deploy the server and admin UI. Configure `HOSTED_MCP_PROXY_BASE_URL` with the externally reachable HTTPS origin before offering proxy mode; deployments without it continue to support disabled/direct choices.
3. Require an administrator to select a mode for each server, review the disclosure, and explicitly sync it. Verify the provider resource and agent version before allowing hosted calls to use it.
4. On rollback, disable hosted integrations and remove only application-owned ElevenLabs MCP resources, verifying provider cleanup first. Retain ownership/status data until cleanup completes; never delete dashboard-owned tools or workflow configuration. Avoid a destructive database rollback while provider resources remain.

## Open Questions

None. Unsupported provider schemas, unavailable public HTTPS reachability, and provider permission failures are explicit fail-closed conditions rather than deferred decisions.
